# Domain docs

This repository uses a single context: `CONTEXT.md` at the root and decisions in `docs/adr/`.

Before exploring domain behavior, read `CONTEXT.md` and the ADRs relevant to the feature. If a referenced document has not been created yet, proceed with the available material.

Use the glossary's canonical terms in code, tickets, and documentation. Keep the glossary limited to domain definitions; record implementation decisions in ADRs and feature behavior in `docs/features/`.

Read ADR status before treating its contents as a decision. Proposed feature ADRs describe future work and unresolved choices, not implemented behavior. Surface conflicts with accepted ADRs explicitly when proposing a change.

Use domain-modeling when resolving terminology or documenting architectural decisions. Create glossary entries and ADRs as those decisions are settled.
